# 嵌入式 Linux 源码排查

先确认问题发生在用户态、内核/驱动、设备树/BSP，还是镜像和启动环节。把开发机、交叉工具链、目标板分开记录；缺少实际板端资料时标注待核对。

## 用户态应用

1. 从项目的 Makefile、CMake、SDK 构建脚本和启动配置定位实际入口、目标、编译器和 sysroot。核对部署版本、目标架构及依赖库。可以用 `readelf -h -l -d` 查产物的架构、解释器和依赖；与目标 rootfs 对照，避免在开发机上执行未知或异构的目标程序。
2. 沿入口、线程或事件循环、I/O 与资源回收追踪。串口、Socket、字符设备分别核对阻塞、部分读写、超时及重连。
3. 先用已有应用日志、配置和复现步骤验证；目标端能读且获准时再采进程状态或 `strace`。采集会改变时序的任务应记录观察扰动。

## 内核、设备树与驱动

1. 找实际内核树和版本、defconfig／配置片段及最终 `.config`，确认 Kconfig 和 Makefile 有没有把驱动编成内置或模块。内核源码版本和板端运行版本分开记录。
2. 找实际选用的 DTS/DTSI、overlay 和启动的 DTB；顺着 `status`、`compatible`、总线、地址、中断、时钟、pinctrl、电源与复位查。源码中存在节点不等于板子当前使用了它。
3. 按总线核对匹配、`probe()`、资源申请和错误返回。区分未匹配、延迟探测、探测失败、驱动已绑定但设备节点未注册。对字符设备继续追踪注册和文件操作，避免把节点权限问题误判成驱动未加载。
4. 有目标板可读证据时，交叉核对板端 `uname -r`、原始 `dmesg`、sysfs 绑定和 `/dev` 节点；不拿开发机的结果替代。如果相关日志受限，记录缺口，不自行提权或修改权限。

只读排查不生成镜像、不替换 DTB、不加载或卸载模块。内核外部模块构建需匹配目标内核的配置和构建产物；构建通过不代表能加载或通过板端功能验证。

参考：[Linux Platform 驱动模型](https://docs.kernel.org/driver-api/driver-model/platform.html) · [内核外部模块构建](https://docs.kernel.org/kbuild/modules.html)。
