# 嵌入式迁移规划

1. 核对源工程和目标各自的根目录、版本、目标配置、板卡和工具链；提取必须保持的产品行为及验证基线。目标型号或版本不明时，给条件性方案并标出阻塞项，不用源侧证据代替目标侧。
2. 根据实际源码、配置、链接脚本、原理图、勘误或版本化文档填写[迁移差异矩阵](assets/migration-plan.md)。对每一项标注「已证实兼容／需适配／待核实／不适用」，给两侧证据和验证办法。把可复用业务、需要重新验证的通用组件和必须更换的板级层分开。
3. MCU／RTOS 按需检查启动和向量、Flash/RAM 与分区、链接地址、时钟、引脚、IRQ/DMA、RTOS 配置、协议和持久化。遇到 Bootloader、OTA 或量产数据，明确地址范围、擦除粒度、保护和回退路径；未确认的写入区间不能进入烧录步骤。
4. 嵌入式 Linux 按需检查目标架构、工具链、sysroot、ABI、依赖库、内核/BSP 与 Kconfig、实际 DTB 和驱动绑定、服务启动、镜像及部署。区分主机测试、交叉构建、模块加载和板端结果。已有设备节点或模块名不等于两个版本兼容。
5. 按依赖安排小步实施：先建立可重复基线，验证最小目标产物，再做受影响接口和异常路径回归。每步给输入、改动范围、成功证据、停止条件和回退办法。用户只请求方案时不修改源码、构建配置、镜像或设备；明确要求保存方案时只写方案文档。获准实施后把矩阵交给开发技能。
