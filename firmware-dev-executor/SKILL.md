# 固件开发执行

先读任务所需的项目记录、硬件接口和产品需求，再按变更依赖小步验证。沿用用户要求的范围：只分析或只给方案时不动工程；只要求构建时只构建目标，不顺手改源码。构建授权不包含烧录、带载或其他板端动作。

核心边界：**人管物理世界，AI 管信息世界。**

- 人负责：上电、带载、观察、温升、过流、异常声音、真实安全、关键产品判断。
- AI 负责：读资料、看源码、看日志、收敛假设、生成最小改动、设计下一轮最小测试。

不要把编译通过当成硬件验证，不要把 AI 的推断当成板端事实。

## 必要上下文

- MCU 或 SoC、板卡版本；必要时补充目标架构、内核版本、工具链或 sysroot。
- 硬件接口速查表、开发板资源模型和危险输出清单。
- 产品行为需求和验收标准。
- 现有项目结构、实际构建入口、目标和构建命令。先核对本轮源码与目标；未确认时，不默认选择工程文件列出的第一个目标，也不沿用未经核对的旧记录。
- 代码分层和命名规则。
- 验证方式：编译日志、串口输出、调试器/SWD、示波器、人工观察。

缺关键上下文时，先建立 TODO 或提出一个聚焦问题，不要编造硬件事实。

## 按任务选择开发顺序

下列顺序适用于 MCU 从零开发或首次调板；根据已验证的底层和当前目标裁剪，不重复带起无关外设。

1. 编译/运行基线。
2. GPIO 安全默认态。
3. UART 日志或最小调试通道。
4. 逐个外设：ADC、PWM、I2C、SPI、定时器、中断、DMA。
5. BSP 抽象：有效电平、板级语义、安全动作。
6. component：parser、CRC、环形缓冲、滤波、参数存储。
7. app 功能模块。
8. app_workflow 业务编排。
9. 集成测试并更新调试记录。

若当前功能依赖尚未验证的底层外设，先验证这个依赖；已确认底层时可以直接处理上层。协议解析、CRC、状态机等可独立验证的改动，优先使用现有主机测试或最小复现，再按需构建目标。

## 嵌入式 Linux 实施

- 用户态应用沿用项目的 Make/CMake、工具链文件、sysroot 和 ABI，记录实际命令和目标。可在主机跑可移植单测；交叉产物另核对架构、解释器和依赖，目标端运行单独验证。
- 驱动或设备树先定位实际板卡和使用的内核/BSP 树，使用该项目的 Kbuild 或 SDK 构建入口。外部模块构建应对应目标内核配置及构建产物；设备树需要核对编译出的 DTB 与启动选择。不要用开发机的内核目录代替目标板的内核构建树。
- 用户态优先核对资源释放、并发和 I/O 错误路径；内核态按可睡眠/原子上下文选择同步和分配方式，用户指针经内核接口访问。MCU 主循环和板级目录规则不套用到 Linux。
- 分开记录编译、部署、模块加载和板端验证。没有部署或设备操作授权时保留可审查的产物及验证步骤，不改设备节点权限、不加载模块、不替换镜像或 DTB。

## 最小测试闭环

每一轮只推进一个最小目标，不要一次改一堆。

标准闭环：

1. 明确一个最小目标  
   例如“让 USART1 打印 BOOT OK”“让 LED0 按 1Hz 闪烁”“读取 W25Q128 ID”“按键按下打印事件”。

2. 明确当前证据  
   读取接口表、需求、手册摘录、现有代码和编译日志，说明依据。

3. 只做最小改动  
   修改最少文件、最少逻辑。不要顺手重构无关模块。

4. 编译或静态检查  
   能编译就编译；不能编译要说明缺什么工具链。

5. 做与改动对应的验证
   纯逻辑优先验证正常及异常输入；涉及引脚、时序、功耗或负载时，说明板端操作和预期现象，例如串口输出、LED、波形、电压或温升。保留实际执行的命令、目标和结果。

6. 按证据决定下一步
   如果下一步依赖尚未取得的板端结果，停在这一验证点，说明需要什么反馈。可独立验证的工作继续做；分别记录源码检查、构建、主机测试、烧录和板端结果，未执行或未确认的项目如实标注。

输出格式：

```markdown
## 本轮最小目标
- ...

## 修改范围
- ...

## 验证方法
- 编译:
- 上板:
- 期望现象:

## 需要人工反馈
- ...

## 下一轮候选
- ...
```

## 架构规则

下列分层约定适用于 MCU／RTOS；嵌入式 Linux 沿用应用、内核或厂商 BSP 的模块和构建结构。

- 裸机新工程可让 `main.c` 保留初始化和调度入口；RTOS 或厂商 SDK 工程沿用其启动、任务和生成代码约定，不强制采用裸机主循环结构。
- `driver` 只表达 MCU 外设机制。
- `bsp` 表达板级含义：引脚、有效电平、安全默认态、硬件资源。
- `component` 必须产品无关。
- `app` 模块负责产品行为。
- `app_workflow` 负责跨模块编排。
- 私有全局变量和私有函数优先使用 `static`。
- 避免失控的全局变量和隐藏跨模块依赖。
- ISR 中不要阻塞，不做复杂耗时逻辑。
- ISR/main 或多任务共享数据必须考虑临界区、锁、队列或原子访问。
- 检查错误码、超时、部分读写、缓冲区边界。

## 安全规则

- 危险输出必须先初始化到安全状态，再使能外设。
- 继电器、电机、加热、阀、高压 PWM、电源使能在未验证前不得带真实负载冒进测试。
- 首次验证危险输出时，优先空载、断开功率级、限流电源或示波器测信号。
- 仅在有对应目标、固件和实际板端证据时，报告已观察到的现象及范围；构建成功、烧录完成都不能代替板端功能验证。
- 需要板端观察时，明确告诉工程师要看什么。

## 编译修复闭环

1. 核对已获准构建的目标和命令，再运行。
2. 完整读取错误和日志。
3. 按根因分组。
4. 只要求构建时，报告错误及证据后停止；本轮允许修复时才修改最小责任范围。
5. 修复后用同一目标重新构建。
6. 记录结果；有改动时说明原因。

同类错误反复出现时，不要盲改，先检查工程文件、include 路径、生成文件、宏、链接脚本和工具链配置。

本轮构建的成功结论必须有对应目标和本轮命令结果。工具缺失、目标未确认或只能找到旧日志时，说明无法验证的原因，不复用旧产物充当新证据。

已安装 `firmware-build-flash-runner` 且匹配项目工具链时，可用它保存本次构建与串口或回放证据。遇到需反复试验的故障，可与 `embedded-debug-loop` 交接；独立复核可用 `firmware-quality-reviewer`。未安装这些技能时，仍可按项目已有工具完成已授权的部分。

## 常见任务的最小目标示例

- GPIO/LED：只验证一个引脚能按安全电平翻转。
- UART：只验证启动打印和回显，不同时加入完整协议。
- I2C：只扫描/读取一个器件 ID 或固定寄存器，不先写复杂业务。
- SPI Flash：只读取 JEDEC ID，不先写擦除。
- PWM：先空载输出低频低占空比波形，不直接接功率负载。
- ADC：先读取固定通道原始值和参考电压，不先做复杂滤波。
- 参数存储：先读默认值和 CRC 校验，不先写入真实生产参数。
- OLED/UI：先显示一行固定文本，再做菜单和按键导航。
- 协议解析：先解析一帧固定样例，再接真实串口流。

## 常见坑

- 代码能编译，但上电不安全。
- 有效电平猜错，继电器或负载误动作。
- 一轮改动太大，无法判断哪个修改引入问题。
- 产品行为没定义清楚，导致代码反复改。
- 小屏 UI 代码逻辑正确，但布局和体验不对。
- 构建、下载、反馈通道没稳定就追求全自动。
