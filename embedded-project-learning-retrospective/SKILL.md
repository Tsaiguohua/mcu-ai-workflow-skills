# 嵌入式项目学习复盘

把一次 AI 协作或阶段性开发沉淀成可学习、可回看、可继续开发的工程笔记。目标不是写日报，而是帮助用户真正掌握项目：知道功能怎么做出来，代码从哪里进、数据怎么流、硬件怎么接、协议怎么跑、旧工程哪些部分被复用或影响。

## 工作原则

- 先读工程和证据，再写复盘。不要只根据聊天印象总结。
- 复盘范围以“本阶段新增/修改内容”为主，但为了讲清实现，必须解释必要的旧工程入口、调用链、数据结构、任务、回调、驱动、UI 或协议代码。
- 文档默认输出到被复盘的工程目录内，而不是全局笔记目录。优先路径：
  - `项目根目录/docs/learning-retrospective/YYYY-MM-DD-功能名.md`
  - 如果项目没有 `docs/`，可创建 `项目根目录/learning-retrospective/YYYY-MM-DD-功能名.md`
  - 如果用户指定路径，按用户指定路径。
- 如果用户只是要方案或口头分析，不要擅自修改源码。若用户要求生成文档，可以创建 Markdown 文件。
- 事实必须绑定证据：源码路径、函数名、日志、构建输出、板端现象、截图、协议样例、硬件资料。推断必须标注“基于现有信息推断”。
- 接入工作流时，可使用上一步留下的项目索引、任务状态、构建日志和调试记录。先核对它们是否对应本阶段的源码、目标和改动，不把前一次验证当成本轮结果。没有配套技能或记录时仍可独立从现有材料复盘。

## 输入证据优先级

按以下顺序收集证据，能读本地工程就不要只靠口述：

1. 用户对本阶段目标、现象和完成状态的描述。
2. Git 状态、`git diff`、新增/修改文件；如果不是 Git 工程，则查看相关源码、构建脚本和最近生成文件。
3. 构建命令、编译输出、运行日志、串口日志、`dmesg`、板端截图或录屏。
4. 程序入口、调用链、任务/线程、中断、回调、信号槽、队列、状态机、共享数据结构。
5. 硬件资料：原理图、引脚表、设备树、外设手册、板卡资料、连接说明、模块型号。
6. 协议资料：UART/CAN/I2C/SPI/USB/TCP/UDP/RTSP/自定义二进制协议、帧格式、字段含义、校验方式。

如果证据不足，先说明缺口；能低风险继续的，可以基于现有信息复盘，但要写清“未确认项”。

## 复盘流程

### 1. 确认项目和阶段范围

确认：

- 项目根目录。
- 本阶段目标。
- 当前是否已完成、部分完成或只是能跑通。
- 用户希望复盘的是今天、本次功能、本次 bug 修复、一次移植，还是一个版本差异。
- 文档保存路径。

需要交接时，另给一段可直接供下轮使用的摘要：工程基线与目标、已确认事实及来源、已尝试动作、未决项和下一步。源码检查、构建、主机测试、烧录、板端观察分开记录。用户只要求口头复盘时直接答复；请求复盘文档时，只写约定的文档。仅在获准更新项目状态时写回已有记录，不重建一套平行文件。

### 2. 梳理修改范围

按模块归类，不要只列文件名：

- 硬件接口：引脚、外设、模块、电源、有效电平、连接方式。
- BSP/驱动：GPIO、UART、I2C、SPI、CAN、ADC、PWM、DMA、摄像头、音频、屏幕、触摸、Flash 等。
- RTOS/并发：任务、线程、队列、消息、信号量、互斥锁、定时器、中断。
- 协议解析：帧头、长度、命令字、状态字段、CRC、粘包拆包、超时。
- 应用逻辑：状态机、业务流程、异常处理、参数保存。
- UI/显示：Qt、LVGL、OLED、LCD、状态卡片、按钮、刷新路径。
- 构建部署：Makefile、CMake、Keil、SCons、交叉编译、动态库、脚本、推送命令。

### 3. 解释软件实现主线

必须从“用户能理解的入口”讲到“代码落点”。优先给调用链和数据流。

调用链示例：

```text
main()
 -> board_init()
 -> app_init()
 -> status_task_entry()
 -> protocol_parse_frame()
 -> device_status_update()
 -> ui_refresh_status()
```

Qt/嵌入式 Linux 示例：

```text
main()
 -> QApplication
 -> MainWindow::MainWindow()
 -> LogReader::loadFile()
 -> ProtocolParser::parse()
 -> DeviceStateModel::update()
 -> MainWindow::refreshUi()
```

数据流示例：

```text
输入：串口/CAN/BIN 文件/摄像头/传感器/用户点击
解析：协议头、长度、命令字、状态字段、校验
存储：结构体、全局状态、模型类、队列、环形缓冲区
触发：任务循环、定时器、信号槽、中断、回调
输出：UI 标签、日志、控制命令、文件、网络推流
```

### 4. 硬件和协议必须单独讲清

如果本阶段涉及硬件、板子、外设或真实设备，文档必须包含：

- MCU/SoC/板卡型号。
- 模块或外设名称。
- 引脚连接表：信号名、MCU 引脚、外设引脚、方向、有效电平、复用功能、上拉下拉、备注。
- 通信接口：UART/I2C/SPI/CAN/USB/以太网/摄像头 DVP/MIPI/音频 I2S 等。
- 关键参数：波特率、I2C 地址、SPI 模式、CAN ID、采样率、分辨率、帧率、电压、时钟、DMA、缓存。
- 协议格式：帧头、长度、命令字、payload、校验、应答、超时、错误码。
- 代码如何使用硬件：初始化函数、读写函数、中断或轮询、任务调度、异常处理。
- 板端验证：如何接线、如何运行、看什么日志、用什么仪器或现象判断成功。

如果没有硬件资料但代码里明显使用外设，要根据源码提取“代码中能确认的硬件事实”，并列出未确认项。

### 5. 旧工程代码要按需解释

用户往往是在旧工程上加新功能。即使复盘重点是新功能，也必须解释被牵涉的旧代码：

- 旧工程的入口在哪里。
- 新功能挂到了哪个旧框架、任务、回调、消息队列、UI 页面或驱动层。
- 新代码复用了哪些旧结构体、全局变量、宏、配置、构建脚本。
- 旧代码的限制如何影响新功能，例如线程安全、刷新周期、缓冲区大小、协议兼容、动态库路径、设备节点。
- 哪些旧代码只是背景，不需要展开；哪些旧代码是理解新功能必须掌握的。

### 6. 问题和修复过程要写成可复盘链条

每个关键问题按这个格式记录：

```markdown
### 问题 N：现象标题
- 原始现象：
- 原始报错/日志：
- 初始猜测：
- 定位过程：
- 实际原因：
- 最终修改：
- 为什么这样改有效：
- 下次如何避免：
```

不要只写“修复了 bug”，要写清从现象到根因的路径。

### 7. 提炼学习点

每个学习点必须绑定代码或硬件证据：

- 技术点名称。
- 它在本项目里解决什么问题。
- 对应文件、函数、结构体或引脚。
- 初学者容易误解的点。
- 用户下次需要重点看的代码位置。

示例：

```markdown
### 技术点：RT-Thread 消息队列
- 用途：把串口解析结果从接收任务传给 UI 刷新任务。
- 代码位置：`app/status_task.c`、`ui/status_page.c`
- 关键点：队列传的是状态快照，不要让 UI 直接读 ISR 内部缓冲区。
```

## 输出风格

- 面向正在学习嵌入式的用户解释，先讲直觉，再映射到源码。
- 不要用空泛词，例如“优化了架构”“增强了稳定性”，除非说明具体改了什么。
- 代码讲解要点名到函数、结构体、字段、宏、文件。
- 硬件内容不能只写“用了串口/I2C”，要写连接、参数、协议、验证方式。
- 最后给 3 到 8 个自测问题，帮助用户确认自己是否真正理解。
